# MR9A fan stop feasibility — 2026-11-09

> Paths under `work/` name files of the local workspace. They are not published: they hold vendor firmware bytes, tool output or machine identifiers.

## Answer

Yes: the fan-control silicon supports zero PWM output and automatic temperature-driven restart. The existing MR9A CPU Smart Fan setup already exposes a four-point PWM curve with a permitted first PWM value of zero. A new BIOS binary may therefore be unnecessary for the CPU channel. Actual fan stop and reliable restart remain dependent on the installed fan and must be measured physically; no fan-duty changes, firmware flash or reboot were performed in this investigation.

## Current hardware evidence

`live-controller.json` and `live-controller-confirmation.json` were read from the running MR9A PRO V1.2 using `read_controller.py`. Only register-access selectors were written; LDN and HWM bank selection were restored. This does not change cooling policy.

- Super I/O ID C562 (NCT5532 family), HWM enabled at A20, indexed access A25/A26.
- CPU: bank2/02=45, Smart Fan IV with tolerance 5; source bank2/00=10, PECI Agent0. Curve temperatures 30/40/50/60; PWM 150/170/200/255. Critical threshold 60; critical-duty enable 0, meaning full speed.
- CPU current output 150/255; RPM sample 1328. The lowest curve PWM is already enough to explain the nonzero output.
- SYS: bank1/02=00, manual output FF/full; source bank1/00=11, PECI Agent1. Curve points all zero/inactive. SYS RPM sample zero does not establish which physical header is populated or controlled.
- PECI alive bank7/1F=01: Agent0 alive, Agent1 not alive in this snapshot. This strengthens the previously conditional SYS source concern. Physical header routing remains unverified.

Smart Fan routine RVA1658 reads the 28-byte `NCT5532D_SMF` variable. CPU fields: mode +00; manual PWM +01; temperatures +02..05; PWM +06..09; critical temperature +0A; critical full/custom +0B; critical duty +0C; tolerance +0D. SYS repeats at +0E.

In automatic CPU mode it copies PWM1 directly to table byte 3CF, eventually written to bank2/27. There is no nonzero minimum clamp. CPU source row at PE offset3F4 selects Agent0; SYS row at478 selects Agent1. These are extracted-PE offsets, not SPI offsets.

The existing Setup IFR explicitly permits PWM1=0..255. CPU controls are visible; SYS mode and related controls are inside an unconditional SuppressIf True at IFR E774. The CPU manual PWM control also accepts zero but manual mode alone supplies no automatic temperature restart and is not the desired operating policy.

`smartfan-disassembly.txt` is a fresh objdump of the beginning of the actual routine. Full prior decompilation is in `work/analysis/reverse-engineering/audit-20261107/native/thermal/exports/mr9a/SioDxeInit.c`.

`verify_zero_policy.py` executes the original x64 routine using the existing Unicorn I/O/GetVariable harness. Twelve cases (PWM1 0/1/64/150 and three initial register states) verify direct propagation, curve temperatures, automatic mode and critical full-speed selection. See `zero-policy-validation.json`. This validates programming behavior, not the silicon curve engine or a physical fan.

## Temperature-triggered restart

Nuvoton's NCT5532D rev1.2 datasheet, sections 8.8 and 8.9, documents Thermal Cruise and Smart Fan IV. Thermal Cruise explicitly decreases to zero below its low temperature range and starts from a programmable nonzero startup duty when heat rises. Relevant per-channel registers: 00 bit7 (retain minimum versus allow zero in Thermal Cruise), 01 target, 02 mode/tolerance, 05 minimum/stop stage, 06 startup duty, 07 stop delay, 35 critical temperature. Stop/start register values should remain nonzero as specified; clearing the documented floor behavior is different from blindly writing zero to every register.

Smart Fan IV uses temperatures 21..24 and PWM 27..2A with tolerance and critical override. A zero lower curve point is the existing-UI route; increasing temperatures command increasing output. A curve can provide a zero-output low-temperature interval and a subsequent rising interval. It should not be promised as an exact binary on/off threshold without a physical response test. Thermal Cruise is an alternative for explicit target-band stop/restart and a startup duty; current firmware auto mode selects Smart Fan IV instead, so enabling Thermal Cruise would require a policy-code change.

Thresholds use the controller's selected PECI-derived temperature scale. Nuvoton cautions that Tbase + relative PECI is not automatically an absolute CPU die temperature. Calibrate against the host CPU readings before interpreting a setup value as a physical Celsius threshold.

## Concrete implementation paths

1. CPU: use existing Automatic mode, choose zero for the low PWM point(s), preserve a rising curve and critical Full Mode. Determine a reliable restart duty for the installed fan and validate cooling/ramp behavior. Existing firmware already supports expressing the zero-bottom curve.
2. SYS: expose the hidden SYS controls and configure a real curve. Live evidence supports replacing its Agent1 source with alive Agent0 if CPU temperature is the intended policy. The final source literal is module byte47B, 11 to10. Confirm header mapping before deployment.
3. If a precise stop/restart band plus startup kick is required, add Thermal Cruise policy controls or modify initialization to program that supported hardware mode. A controller-owned policy can operate without an OS fan-control service.

No candidate full ROM was needed to answer feasibility, and none was built or flashed. No physical fan stop/restart has been demonstrated. Fan models and header mapping are the remaining physical unknowns, not whether the controller or original CPU BIOS path can represent zero.
